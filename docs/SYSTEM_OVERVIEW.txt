============================================================
WHAT THIS SYSTEM IS
============================================================

Quanta is a professional modular forex trading operating system.
It is designed for ONE solo trader to:
  1. Research and validate strategies using historical data
  2. Run risk-first live execution on a funded account
  3. Monitor everything from a single Streamlit dashboard
  4. Protect capital with multiple safety layers

This is NOT a "robot" that you run and forget.
You monitor it daily.  You understand every decision it makes.
The dashboard shows you everything.  You have kill switch on your phone.

DATA FLOW (LIVE TRADING)
============================================================

MT5 terminal
  → core/pulse.py          (publishes RAW_MARKET_DATA events)
  → tick_sanitizer          (validates, rejects bad ticks, re-publishes clean MARKET_DATA)
  → market_data_hub         (stores in DuckDB)
  → [every H1 close] regime_detector (multi-factor vote/validation/transition → RegimeState)
  → [REGIME_CHANGED + REGIME_PROBABILITY + REGIME_TRANSITION] orchestrator/scoring context
  → strategies              (pure SignalEvent generation from candles + injected context)
  → [SIGNAL_GENERATED] scoring_engine (quality score 0-100)
  → [score ≥ 60] risk/shield  (DD check, kill switch check)
  → [approved] execution/router  (gate checks → MT5 order)
  → [TRADE_FILLED] execution/profiler (slippage tracking)
  → [TRADE_FILLED] repositories/trade_repository (SQLite)

IMPORTANT DATA BOUNDARY:
  RAW_MARKET_DATA is raw broker input and must only be consumed by tick_sanitizer.
  MARKET_DATA is clean broker input and must contain sanitized=True.
  market_data_hub rejects unsanitized MARKET_DATA payloads.
  No strategy, regime detector, backtest, or repository may consume raw ticks.

REGIME ENGINE NOTES (V2+):
  - H1 requirement remains strict for live classification.
  - Insufficient history produces WAITING/DEGRADED status (no forced regime).
  - Strategy mapping is advisory to strategy selection; indicators never place trades.
  - Research taxonomy supports 52 analytical regimes grouped into 10 categories.
  - Live risk/execution uses 12 operational regime labels and 4 operating quadrants.

============================================================
STARTUP ORDER (LIVE / VPS)
============================================================

The system must boot in this exact order:

  1. Load .env and YAML config.
  2. Verify Redis/system registry is reachable.
  3. Run RecoveryManager before starting live workers:
       - record restart
       - restore last SQLite state snapshot
       - restore kill switch if it was active
       - rebuild daily DD
       - reconcile MT5 in LIVE mode
       - detect orphan trades
  4. Start in-process event subscribers:
       - tick_sanitizer first
       - market_data_hub second
       - data_quality_monitor
       - session_filter
       - regime_detector
       - kill_switch
       - correlation_guard
       - execution_profiler
  5. Start long-running workers:
       - config_registry
       - clock
       - heartbeat
       - shield
       - ATR engine
       - pulse (raw MT5 ticks) only after sanitizer and hub are subscribed
       - broker_bridge
       - trade_logger
       - order_tracker
       - trade_manager
  6. Mark safe_to_trade only if:
       - recovery succeeded
       - kill switch is not active
       - critical subscribers are running
       - broker state is reconciled or TEST mode explicitly skipped reconciliation

If any critical startup step is uncertain, the system must fail closed:
  activate kill switch, block trading, show the reason on dashboard.

DEPENDENCY AND IMPORT RULES
============================================================

Allowed direction:
  core/          → must not import systems/risk/execution/dashboard
  services/      → may import core only
  repositories/  → may import core + services
  systems/       → may import core + services + repositories
  strategies/    → may import core models/enums/constants and feature helpers only
  risk/          → may import core + repositories
  execution/     → may import core + repositories + risk decisions, not strategies
  dashboard/     → may import read APIs and safe control APIs only
  orchestrator/  → may import all runtime modules because it owns startup control

Strict rules:
  - No broker/MT5 logic inside strategies.
  - No risk approval logic inside execution.
  - No dashboard shortcut may bypass risk/router/kill-switch checks.
  - No raw SQL outside repositories and storage_service.
  - No raw broker tick may bypass tick_sanitizer.
  - Strategies should stay pure: same candles + context must produce same signals.

============================================================
FAIL-SAFE RULES
============================================================

Default policy: uncertainty blocks trading.

Reject trade and require manual review when:
  - kill switch is active or kill switch state is unknown
  - recovery report has orphan trades
  - broker/local state reconciliation fails
  - MT5 is disconnected or account type is unexpected
  - data feed is stale or unsanitized
  - spread/slippage/latency thresholds are exceeded
  - funded rule state cannot be calculated
  - config file is missing, invalid, or cannot be reloaded

The system must never fail open.
When unsure: publish an alert, log to audit/error, keep capital protected.

RUNTIME MODES
============================================================

Current environment parser:
  core/system_mode.py supports TEST and LIVE from .env.

Operational modes used by runtime state:
  RESEARCH   — offline data analysis only
  BACKTEST   — historical simulation only
  DEMO       — broker demo account, no real/funded money
  LIVE       — funded/real account, strict controls
  EMERGENCY  — kill switch active; all new order submission blocked

Required next alignment:
  system_mode.py should be expanded to support DEMO/RESEARCH/BACKTEST/EMERGENCY
  or documented as environment mode only while state_store owns runtime mode.

============================================================
LATENCY AND EXECUTION TARGETS
============================================================

Execution quality must be measurable and visible.

Targets:
  Internal event handler normal latency: < 50 ms
  Slow event handler warning:          > 200 ms
  MT5 order submit → broker ack target: < 500 ms
  Execution profiler latency alert:    > 2000 ms average
  Kill switch latency threshold:       > 5000 ms average
  XAUUSD normal slippage target:       < 0.5 pips
  Slippage warning:                    > 1.0 pip average
  Hard review threshold:               > 2.0 pips average

All routing/fill events must log:
  correlation_id, order_id, trade_id, symbol, direction, requested price,
  fill price, slippage_pips, latency_ms, spread_at_fill, broker response.

DASHBOARD BOUNDARY
============================================================

Dashboard is an operator control surface, not a trading shortcut.

Allowed:
  - view system health
  - view trades, logs, recovery, regime, data quality
  - edit YAML config after validation
  - manually activate/reset kill switch
  - run local research tools (backtest, walk-forward, Monte Carlo)

Not allowed:
  - bypass router/risk checks
  - send broker orders directly
  - silently reset kill switch after crash
  - edit persisted trade history without audit logging
  - promote DEMO to LIVE without explicit operator confirmation

============================================================
RECOVERY FLOW
============================================================

RecoveryManager runs once at startup before ticks or execution workers.

Recovery steps:
  1. Record restart in logs/restart_log.json.
  2. Load latest SQLite state snapshot.
  3. Restore kill switch state. If active before crash, keep it active.
  4. Rebuild daily DD from local trade records.
  5. In LIVE mode, query MT5 open positions.
  6. Compare MT5 positions vs local open trades.
  7. Mark orphan trades for manual review.
  8. Write logs/recovery_log.json.
  9. Publish RECOVERY_COMPLETE event.

Operator rule:
  If orphan trades or reconciliation issues exist, trading stays blocked until
  the operator verifies broker state manually.
