============================================================
WHAT IT DOES
============================================================

StorageService is the single gateway to all databases.
No other module accesses databases directly.
All writes and reads go through this service.

TWO DATABASES:

DuckDB (market.duckdb) — Time-series / analytical data:
  - Ticks (bid, ask, spread, timestamp)
  - Candles (OHLCV for all timeframes)
  - Backtest results and equity curves
  - Regime history

SQLite (journal.db) — Transactional / operational data:
  - Trades (entry, exit, PnL, status)
  - Signals (generated and blocked)
  - State snapshots (equity, DD)
  - Kill switch history
  - Execution fills (slippage, latency)
  - Restart logs

============================================================
KEY METHODS
============================================================

# SQLite reads (thread-safe, no lock needed)
rows = storage.execute_sqlite("SELECT * FROM trades WHERE status='OPEN'")

# SQLite writes (serialized with write lock)
storage.execute_sqlite_write(
    "INSERT INTO trades VALUES (?, ?, ?)",
    params=(trade_id, symbol, status)
)

# DuckDB reads
rows = storage.execute_duckdb("SELECT * FROM candles WHERE symbol='XAUUSD'")

# DuckDB writes (single-writer lock)
storage.execute_duckdb_write("INSERT INTO candles VALUES (?, ?, ?)", params=(...))

# Health and stats
stats = storage.get_stats()
# Returns: db sizes, row counts, avg read/write latency

============================================================
RETRY LOGIC
============================================================

SQLite writes are retried up to 3 times with exponential backoff:
  Attempt 1: immediate
  Attempt 2: wait 0.5 seconds
  Attempt 3: wait 1.0 seconds

If all retries fail, a StorageError is raised and logged.

This handles the common "database is locked" error from SQLite
when multiple threads try to write simultaneously.

============================================================
CONNECTION POOLING
============================================================

SQLite:
  - Single shared connection with check_same_thread=False
  - WAL mode enabled for better read concurrency
  - Write-lock (RLock) ensures serial writes

DuckDB:
  - Single connection (DuckDB requirement)
  - Single write-lock protects concurrent write attempts
  - Read operations can happen concurrently (DuckDB handles it)

============================================================
IMPORTANT RULES
============================================================

1. NEVER import StorageService inside a hot loop.
   Get a reference once at startup, reuse it.

2. NEVER bypass StorageService to connect to DB directly.
   All raw DB access creates untestable, fragile code.

3. execute_sqlite and execute_sqlite_write are DIFFERENT:
   - execute_sqlite: read-only, no lock needed
   - execute_sqlite_write: acquires write lock, retries on failure

4. DuckDB is NOT suited for high-frequency row-by-row inserts.
   Batch inserts when possible (use DuckDB's multi-row INSERT).
